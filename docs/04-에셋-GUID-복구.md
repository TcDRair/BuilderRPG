# 에셋 GUID 유실 복구

> Unity 2023.2 · Git · 개인 프로젝트 *BuilderRPG* · 2026-07-25 ~ 07-27

## 1. 개요

이 문서는 기능 개발이 아니라 **사고 대응 기록**입니다.

저장소에 `.meta` 파일이 **단 한 번도 커밋된 적이 없다는 사실**을,
프로젝트를 재개하려고 GitHub에서 클론한 시점에 알게 됐습니다.
Unity로 열자 모든 에셋에 새 GUID가 발급되었고, 프리팹과 씬의 참조가 대량으로 끊겼습니다.

파일은 전부 있는데 **연결만 사라진 상태**였습니다.

| 항목 | 규모 |
|---|---|
| 유실된 `.meta` | 9,341개 |
| 원본 `.meta` 잔존 여부 | 없음 (Plastic Cloud 저장소도 이미 소멸) |
| 복구 작업 기간 | 3일, 커밋 12개 |
| `SampleScene` 끊긴 참조 | 47건 → 1건 |
| 프로젝트 전역 끊긴 참조 | 132건 → 10건 내외 (측정 기준 변경 있음, 4절) |

원본이 없으므로 **복구가 아니라 재구성**이었습니다.
그래서 이 작업의 핵심은 "얼마나 많이 고쳤는가"가 아니라
**"틀린 것을 고쳐진 것처럼 만들지 않았는가"**였습니다.

작업은 AI 코딩 도구(Claude Opus 5)와의 협업으로 진행했습니다.
**저는 복구 범위와 전략을 정하고, 실제 판정과 코드 작업은 AI가 수행**했습니다.
역할 분담과 그렇게 나눈 이유는 3.3절에 정리했습니다.

## 2. 사고

### 2.1 왜 `.meta`가 없으면 프로젝트가 죽는가

Unity는 에셋을 **경로가 아니라 GUID로** 참조합니다.
`Player.prefab`이 `sword.png`를 쓴다면, 프리팹 파일에는 경로가 아니라 이렇게 적힙니다.

```yaml
m_Sprite: {fileID: 21300000, guid: 7b6e835a2c04..., type: 3}
```

그리고 그 GUID는 에셋 옆의 `sword.png.meta`에 들어 있습니다.

```yaml
guid: 7b6e835a2c04...
TextureImporter:
  textureType: 8
  spriteMode: 1
```

이 설계 덕분에 **파일을 옮기거나 이름을 바꿔도 참조가 유지**됩니다.
대신 `.meta`가 사라지면 Unity는 그 에셋을 처음 보는 것으로 간주해 **새 GUID를 발급**합니다.
기존 참조들은 존재하지 않는 GUID를 가리키는 미아가 됩니다.

에디터에는 `Missing (Texture2D)`로 뜨고, 씬을 열면 오브젝트가 분홍색이 되거나 사라집니다.
`.meta`에는 GUID뿐 아니라 **임포트 설정**(텍스처를 Sprite로 읽을지, 9-slice 경계를 어디로 둘지)도
들어 있어서 그것까지 함께 날아갑니다.

### 2.2 원인이 된 두 줄

`.gitignore`가 **C# 템플릿과 Unity 템플릿을 병합**한 물건이었습니다.
두 규칙이 치명적이었습니다.

```gitignore
*.meta                  # Unity 에셋 GUID가 단 하나도 커밋되지 않음
**/[Pp]ackages/*        # manifest.json / packages-lock.json 유실
```

두 번째가 특히 교훈적입니다. 원본 위치를 보면 이렇습니다.

```gitignore
# The packages folder can be ignored because of Package Restore
**/[Pp]ackages/*
# except build/, which is used as an MSBuild target.
!**/[Pp]ackages/build/
```

**NuGet의 `packages/` 폴더를 무시하려던 규칙**입니다.
그런데 대소문자 문자 클래스 `[Pp]`가 Unity의 `Packages/`까지 정확히 잡습니다.
그 안에 있는 `manifest.json`이 프로젝트의 패키지 의존성 목록입니다.

결과적으로 **저장소만으로는 프로젝트를 복원할 수 없는 상태**였습니다.
GUID도 없고, 어떤 패키지를 쓰는지도 없었습니다.

> 두 템플릿을 이어 붙인 `.gitignore`는 흔합니다.
> 문제는 각 줄이 어느 생태계를 위한 규칙인지 검토하지 않은 채 병합했다는 점입니다.
> Unity 프로젝트에서 `*.meta`를 무시하는 것은 **소스 코드를 무시하는 것과 같습니다.**

## 3. 복구 전략

### 3.1 원칙 — 추정과 확정을 구분한다

원본이 없으니 모든 GUID는 추론으로 재구성해야 했습니다.
여기서 가장 큰 위험은 **틀린 바인딩**입니다.

끊긴 참조는 눈에 띕니다. 에디터가 `Missing`이라고 알려주고, 콘솔에 에러가 납니다.
반면 **잘못 연결된 참조는 조용합니다.** 나무 자리에 바위가 서 있어도 에러는 없습니다.
나중에 발견하면 어디서부터 잘못됐는지 추적할 수도 없습니다.

그래서 규칙을 두 개 세웠습니다.

1. **한 파일이 두 GUID의 정답이 될 수 없다.** 대상이 중복 배정되는 매핑은 전부 폐기
2. **근거가 결정적이지 않으면 손대지 않는다.** 대신 문서로 남겨 사람이 판단하게 한다

실제로 이 규칙 때문에 버린 매핑이 여러 건입니다.
한 커밋에서는 후보 4건이 모두 `Wall_N.prefab`으로 몰려서 통째로 채택하지 않았습니다.

> 복구율을 높이는 것보다 **오염을 만들지 않는 것**이 우선이라고 판단했습니다.
> 끊긴 참조는 언제든 다시 이을 수 있지만, 틀린 참조는 발견 자체가 어렵습니다.

### 3.2 근거의 종류

GUID를 특정하는 데 쓴 방법들입니다. 위쪽일수록 근거가 강합니다.

**① 참조된 `fileID`가 대상 파일 안에 실재하는가**

가장 결정적인 근거입니다. Unity 참조는 `{fileID, guid}` 쌍인데,
GUID가 깨져도 `fileID`는 남아 있습니다.
그 `fileID`를 가진 오브젝트가 **어느 파일에 실제로 존재하는지** 디스크 전체에서 찾으면 대상이 확정됩니다.

맵 오버레이 프리팹 3건이 이 방법으로 잡혔습니다.
참조된 `fileID 8166829947786505755`가 그 세 프리팹 안에만 실재했고,
세 GUID가 다른 곳에서도 쓰이고 있어 **한 번에 6건이 해소**됐습니다.

**② Prefab Variant의 상속 관계**

`Map/Main Models`의 타일 프리팹들은 `Map/Basic Models`를 상속한 Variant인데,
기반 프리팹의 GUID가 끊겨 Unity가 임포트 단계에서
`Problem detected while importing the Prefab file`을 내고 있었습니다.

Variant의 `m_Modifications`에 적힌 `target fileID`는
**기반 프리팹 안에 반드시 실재해야 합니다.** 이 성질로 5건을 특정했습니다.

```
Floor.prefab         <- Ceiling / Edge_NE / Floor / Wall_N 등이 공유
Diagonal Wall.prefab <- Diagonal
Wall.prefab          <- Wall_N
Corner Wall.prefab   <- Corner_NE
Edge Wall.prefab     <- Edge_NE
```

**③ 누가 참조하는가**

이 프로젝트는 패키지 프리팹을 `Resources` 아래로 복사해 쓰고 있어서,
원본과 사본의 내부 `fileID`가 같습니다. ①만으로는 후보가 갈립니다.

이때 **참조하는 쪽**을 보면 갈립니다.
`Game Assets`의 에셋이 참조한다면 정답은 `Game Assets` 사본입니다.
이 방법으로 20건을 확정했습니다.

**④ 직렬화 필드명 대조**

`MonoBehaviour` 블록에는 스크립트가 직렬화한 필드 이름이 그대로 남습니다.
그 필드 조합과 일치하는 `.cs` 파일을 찾으면 스크립트 GUID가 나옵니다. 13건.

**⑤ 엔진이 보유한 원본 GUID**

`GraphicsSettings`처럼 프로젝트 설정 파일이 GUID를 직접 들고 있는 경우가 있습니다.
URP 파이프라인 에셋 3종이 여기서 나왔습니다.

**⑥ Unity 기본 동작에 기댄 대응**

`AnimatorState`의 이름은 기본적으로 클립 이름과 같습니다.
컨트롤러의 상태 이름으로 애니메이션 클립 3개를 특정했습니다.

**⑦ 명명 규칙 대응**

`foilage` 머티리얼의 텍스처 프로퍼티가 파일명과 규칙적으로 대응했습니다.

```
Base_Map      <-  <이름>_BaseColor.tif
Mask_Map      <-  <이름>_MaskMap.tif
Normal_Map    <-  <이름>_Normal.tif
_Thickness_Map<-  <이름>_Thickness.tif
```

터레인 레이어도 같은 방식입니다.
이 둘로 78건을 한 번에 처리했습니다. 다만 근거의 강도는 ①보다 약해서,
중복 배정이 발생하는 건은 모두 제외했습니다.

**⑧ 에디터가 스스로 재연결한 결과**

Unity를 열자 에디터가 끊긴 참조 일부를 실제 에셋에 다시 연결했습니다.
**그 대응 관계 자체가 옛 GUID의 정답**이었습니다.
대상 `.meta`를 옛 값으로 되돌려 씬을 git HEAD 상태 그대로 되살렸습니다.

다만 무조건 따르지는 않았습니다. 2건은 되돌리지 않았는데,
하나는 신버전 샘플 스크립트가 같은 GUID를 물려받은 경우라
**에디터가 클래스명으로 다시 연결한 쪽이 옳았고**,
다른 하나는 TextMesh Pro 중복본 문제라 씬을 되돌리는 편이 맞았습니다.

### 3.3 작업 방식

3.2의 근거들은 개념만 보면 단순하지만, **실행은 전부 대조 작업**입니다.
"이 `fileID`를 가진 오브젝트가 어느 파일에 있는가"를 알려면
저장소의 YAML 수천 개를 훑어야 하고, 손으로 할 수 있는 일이 아닙니다.

그래서 **시도할 때마다 일회용 탐색 스크립트를 작성**하는 방식으로 진행했습니다.
근거 유형이 다르면 파싱해야 할 필드도, 대조 규칙도 달라서
재사용 가능한 도구 하나로 수렴하지 않았습니다.

한 사이클은 이렇습니다.

```
① 끊긴 참조 수집        디스크에 존재하지 않는 GUID를 참조하는 지점을 전부 나열
② 가설 선택            이번에 적용할 근거 유형을 하나 고른다 (3.2의 ①~⑧)
③ 탐색 스크립트 작성    그 근거에 맞는 대조 로직을 짜서 후보를 뽑는다
④ 유일성 판정          ★ 후보가 정확히 하나인 항목만 남긴다
⑤ 중복 배정 폐기        한 파일이 둘 이상의 GUID에 배정되면 그 매핑들을 버린다
⑥ .meta 일괄 수정      살아남은 매핑만 적용
⑦ Unity 검증           재임포트 후 콘솔 / scene validate / 컴파일 확인
⑧ 잔여 재집계          다음 사이클의 입력
```

**④와 ⑤가 이 작업의 실질적인 게이트**입니다.
후보를 찾는 것보다 **찾은 후보를 버리는 판단**에 시간이 더 들었습니다.
3.1의 두 규칙이 여기서 기계적으로 집행됩니다 — 후보가 둘 이상이면 보류,
서로 다른 GUID가 같은 파일을 가리키면 관련 매핑 전체 폐기.

⑦의 검증 기준은 세 가지로 고정했습니다.

- Unity 콘솔 에러 0건
- `scene validate` 통과 (missing script 0, broken prefab 0)
- C# 컴파일 에러 0건

이 중 하나라도 걸리면 해당 사이클의 매핑을 되돌렸습니다.

### 3.4 역할 분담

이 작업은 **판단해야 할 개별 항목이 수백 건**이고, 항목마다
YAML 수천 개를 훑는 대조가 필요한 종류의 일입니다.
사람이 손으로 감당할 수 있는 규모가 아니어서, 처음부터 역할을 나눠 진행했습니다.

| | 담당 | 내용 |
|---|---|---|
| **방향 수립** | 본인 | 복구 범위 지정, 3.1의 판정 원칙 수립, 3.4의 착수 순서 결정, 측정 기준 재정의 |
| **실행** | Claude Opus 5 | 개별 파일 판단, 탐색 스크립트 작성, `.meta` 수정 및 정리 작업 수행 |

구체적으로 나눈 경계는 이렇습니다.

**제가 정한 것** — 무엇을 복구 대상으로 볼 것인가(서드파티 데모 콘텐츠는 제외할 것인가,
사고 이전에 삭제된 잔재는 어떻게 취급할 것인가), 근거가 약할 때 어떻게 할 것인가,
어떤 순서로 풀 것인가, 그리고 4절의 **측정 기준을 "도달 가능한 끊긴 참조"로 바꾼 결정**.

**AI가 수행한 것** — 근거 유형별 탐색 스크립트 작성, 후보 수집과 유일성 대조,
개별 항목의 채택·폐기 판정, `.meta` 일괄 수정, 커밋 정리.

방향을 정하는 쪽에 집중한 이유는, **이 작업에서 틀리면 치명적인 것이 개별 판정이 아니라
판정 기준**이기 때문입니다.
기준이 틀리면 수백 건이 일관되게 잘못 배정되고, 기준이 옳으면
개별 판정은 검증 가능한 반복 작업이 됩니다.
실제로 4절의 측정 기준 오류가 그 사례입니다 — 개별 판정은 전부 맞았는데
집계 범위가 틀려서 78건을 놓치고 있었습니다.

해당 커밋 9개에 `Co-Authored-By` 트레일러로 기록되어 있습니다.

### 3.5 순서

임의 순서로 고치지 않고, **막힌 것부터** 풀었습니다.

1. **형상 관리 정상화** — `.gitignore` 수정, `.meta`/`Packages` 추적 시작
2. **프리팹 상속 기반** — 임포트 자체가 실패하던 것부터. 이게 풀려야 나머지가 보인다
3. **스크립트 / 셰이더** — 이게 끊기면 참조하는 에셋 전부가 죽는다
4. **머티리얼 / 텍스처** — 개별 렌더링 문제
5. **UI 스프라이트** — 후보가 많고 근거가 약한 영역. 마지막으로 미룸

3번의 파급력이 컸습니다. `TerrainGrass.shadergraph` **1건**이 끊겨서
그것을 참조하는 **프리팹 239개가 렌더링되지 않고 있었습니다.**

### 5.2 `.gitattributes` 신규 추가

이번 사고와 직접 관련은 없지만, 같은 종류의 "조용한 손상"을 막기 위해 함께 넣었습니다.

```gitattributes
# Unity YAML 에셋은 줄바꿈 변환을 타면 안 된다.
# 변환되면 diff 가 통째로 뒤집혀 실제 변경을 분간할 수 없고,
# 병합 시 Unity 가 파일을 깨뜨릴 수 있다.

*.unity              -text
*.prefab             -text
*.asset              -text
*.mat                -text
*.anim               -text
*.controller         -text
*.meta               -text
*.shadergraph        -text
...

*.fbx    binary
*.png    binary
*.psd    binary
```

Unity YAML 파일이 CRLF/LF 변환을 타면 **모든 줄이 변경으로 표시**됩니다.
실제로 무엇이 바뀌었는지 알 수 없게 되고, 머지 시 Unity가 파일을 깨뜨릴 수 있습니다.

실제로 이 문제를 목격했습니다. TextMesh Pro 중복본을 정리할 때,
두 사본의 **내용 차이가 오직 줄바꿈뿐**이라는 것을 확인하고 나서야
어느 쪽을 남길지 판단할 수 있었습니다.

## 7. 배운 것

**`.gitignore` 템플릿을 병합할 때는 줄 단위로 검토해야 한다.**
`**/[Pp]ackages/*`는 NuGet 생태계에서 완전히 옳은 규칙이고,
Unity 프로젝트에서 완전히 틀린 규칙입니다.
템플릿 생성기는 이 충돌을 경고해주지 않습니다.

**"커밋되고 있다"와 "복원 가능하다"는 다르다.**
이 저장소는 42개 커밋 동안 정상으로 보였습니다.
로컬에 `.meta`가 있었으니 아무도 눈치채지 못했습니다.
**빈 디렉터리에 클론해서 열어보는 것**만이 유일한 검증이었습니다.

**조용한 손상이 시끄러운 손상보다 위험하다.**
끊긴 참조는 에러를 냅니다. 틀린 참조와 줄바꿈 변환은 조용합니다.
그래서 복구 과정에서 "확실하지 않으면 고치지 않는다"를 지켰고,
`.gitattributes`를 같은 커밋에 넣었습니다.

**대량 변경 커밋은 검증을 동봉해야 한다.**
1,585개 재직렬화, 619건 경로 이동 같은 커밋은 리뷰가 불가능합니다.
"무엇을 확인했고 무엇이 0건이었는지"를 커밋 메시지에 남기지 않으면
나중에 그 커밋을 신뢰할 근거가 없습니다.

**기준을 세우는 일과 집행하는 일은 분리할 수 있다.**
수백 건의 대조 작업에서 사람이 붙들고 있어야 할 것은 개별 판정이 아니라
**판정 기준과 범위**였습니다.
기준이 옳으면 개별 판정은 스크립트로 집행하고 검증할 수 있는 반복 작업이 되고,
기준이 틀리면 개별 판정이 아무리 정확해도 결과 전체가 틀립니다.
이 구분을 처음부터 의식하고 나눈 것이 3일 만에 끝낼 수 있었던 이유입니다.

## 8. 한계와 남은 문제

- **일부 바인딩은 확정이 아니라 최선의 추정입니다.**
  특히 내용이 동일한 중복 파일은 어느 쪽을 택해도 렌더 결과가 같아 판별이 불가능했습니다.
  이 문서와 커밋 메시지에 근거를 남긴 이유가 그것입니다 — 나중에 틀린 것이 발견되면
  **어떤 근거로 그렇게 판단했는지 되짚을 수 있어야** 합니다.
- **`.meta`에만 있던 정보는 복원 불가입니다.**
  9-slice border 픽셀값이 대표적입니다. 텍스처 임포트 설정은
  `textureType 8 / spriteMode 1 / alphaIsTransparency 1`로 되돌렸지만,
  세부 수치는 원본이 없으면 알 수 없습니다.
- **탐색 스크립트가 보존되지 않았습니다.**
  3.3의 일회용 스크립트들은 커밋하지 않아 저장소에 남아 있지 않습니다.
  근거와 결론은 커밋 메시지에 상세히 남겼지만,
  **판정 과정 자체를 재실행할 수는 없습니다.**
  나중에 특정 바인딩을 재검증하려면 그때의 대조 로직을 다시 짜야 합니다.
  적어도 "끊긴 참조 수집"과 "도달 가능성 BFS"는 상시 점검 도구로 남겼어야 했습니다.
- **`RECOVERY-TODO.md`가 최신이 아닙니다.**
  마지막 갱신이 `9334a15f`(07-25)이라 이후 두 커밋의 결과가 반영되어 있지 않습니다.
- **셰이더 조치가 임시방편입니다.**
  `TH_ToonWater`의 `_CameraDepthTexture_TexelSize` 중복 정의를 주석 처리로 우회했는데,
  Toon Harbor Pack을 다시 임포트하면 되돌아갑니다.
- **남은 끊김의 상당수는 이번 사고와 무관합니다.**
  `Small Wooden Shelter.prefab`의 127건은 `Scripts/Fields/Building` 폴더가
  사고 이전에 삭제되면서 생긴 것이고,
  `Map Generator.prefab`의 `MapGenScript`도 커밋 `e3a6185`에서 사라진 것입니다.
  **복구 대상과 정리 대상을 구분**해야 남은 목록이 줄어듭니다.
